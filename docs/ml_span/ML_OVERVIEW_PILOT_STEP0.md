# ML 탐지기 설명: mmBERT와 Qwen (팀 0단계 합성 데이터)

팀의 0단계 합성 데이터(`promptguard-data` `ml-train-pilot` `5b812c7`)로 학습한 두 종류의 ML 탐지기를 설명합니다. 무엇을 하는 모델인지, 어떻게 학습했는지, 안에서 기술적으로 어떻게 동작하는지 순서로 씁니다.

- **mmBERT**: 글자 위치마다 "비밀값인가"를 표시하는 인코더 모델입니다. 결과는 [PILOT_STEP0.md](PILOT_STEP0.md)에 있습니다.
- **Qwen**: 비밀값을 그대로 다시 써 주는 생성형 모델입니다. 결과는 [QWEN_PILOT_STEP0.md](QWEN_PILOT_STEP0.md)에 있습니다.

숫자는 모두 각 모델 자신의 팀 val 결과입니다. 팀 test·test_ood는 열지 않았습니다.

## 한눈에 보기

| | mmBERT | Qwen |
|---|---|---|
| 기본 모델 | `jhu-clsp/mmBERT-small` (인코더, 1.4억 파라미터) | `Qwen/Qwen2.5-Coder-0.5B-Instruct` (디코더, 4.9억 파라미터) |
| 문제를 푸는 방식 | 토큰마다 B / I / O 라벨 분류 | 비밀값과 등장 순번을 JSON으로 생성 |
| 학습하는 부분 | 모델 전체 (1.4억) | LoRA 어댑터만 (880만, 전체의 1.75%) |
| 위치(offset) | 토큰의 글자 위치에서 바로 나옴 | 생성한 값을 원문에서 찾아 복원 |
| 점수 | span 토큰들의 비밀 확률 평균 | 값 토큰들의 생성 확률 기하평균 |
| 학습 시간 (Colab T4) | A 약 68분, B 약 110분 | A 약 6시간, B 약 8시간 |
| A val (정답 435) | 388 / 47 / 47 · F2 0.892 | 430 / 1 / 5 · F2 0.990 |
| B val (정답 615) | 551 / 55 / 64 · F2 0.899 | 591 / 2 / 24 · F2 0.968 |

표의 숫자는 "맞힘 / 오탐 / 놓침 · F2"입니다. mmBERT는 학습한 그대로의 숫자입니다. 따옴표 정리 후처리를 켜면 높아집니다(아래 2.5).

## 1. 공통: 무엇을 하는 모델인가

### 1.1 문제

AI 코딩 에이전트가 주고받는 텍스트에서 **비밀값이 있는 글자 구간(span)**을 찾습니다. 비밀값은 비밀번호, API 키, 액세스 토큰, 개인키, 연결 문자열 속 비밀번호, 세션 쿠키 같은 것입니다.

- **입력**: 텍스트 한 덩어리. PromptGuard가 검사하는 prompt, instructions, tool_output 채널의 item 하나가 한 행입니다.
- **출력**: `[start, end)` 글자 위치와 점수의 목록. 비밀값이 없으면 빈 목록입니다.
- 규칙 기반 탐지기가 놓치는, 형식이 일정하지 않은 비밀값을 주변 문맥으로 찾는 것이 목적입니다.

### 1.2 데이터

| | 팀 세션 (train / val) | 학습 행 (train / val) | 정답 span (train / val) |
|---|---|---|---|
| A: 손 템플릿 + privesc | 1,108 / 80 | 15,818 / 305 | 5,563 / 435 |
| B: 손 템플릿 + LLM 템플릿 + privesc | 1,693 / 155 | 19,385 / 815 | 6,847 / 615 |

- 정답은 행마다 비밀값의 글자 위치로 주어집니다.
- 대부분의 행은 비밀값이 없는 음성 행입니다. A train은 15,818행 중 3,702행에만 비밀값이 있습니다(23%).
- 두 모델은 **같은 행**으로 학습했습니다. 팀의 train과 val에서 한 행도 빼거나 자르지 않았습니다.
- 데이터는 팀 스크립트로 만들고, 파일 30개의 sha256이 팀 값과 같은지 확인했습니다. 실제 형식의 값과 SSH 키가 들어 있어서 Git에는 올리지 않습니다.

### 1.3 평가 기준

- **exact-span 매칭**: 예측 span의 시작과 끝이 정답과 글자 하나까지 같아야 맞힘(TP)입니다. 한 글자라도 다르면 오탐(FP) 하나와 놓침(FN) 하나가 됩니다.
- **precision** = TP / (TP + FP). 찾았다고 한 것 중 맞은 비율입니다.
- **recall** = TP / (TP + FN). 정답 중 찾은 비율입니다.
- **F2** = 5·P·R / (4·P + R). recall에 precision보다 4배 무게를 둔 조화평균입니다. 비밀값을 놓치는 것이 잘못 잡는 것보다 위험하기 때문입니다.
- **선택 규칙**: epoch과 cutoff는 각 모델 자신의 val F2로만 고릅니다. 팀 test는 선택이 끝난 뒤 팀이 먼저 평가합니다.

## 2. mmBERT 모델

### 2.1 모델 자체

- **기본 모델**: `jhu-clsp/mmBERT-small`(revision `abc3262`). 여러 언어 텍스트로 사전학습한 다국어 인코더이고, 구조는 ModernBERT입니다.
- **구조** (`models/span-pilot-step0-a-seed110/config.json`):
  - Transformer 인코더 22층, hidden 384, attention head 6개, FFN 1,152.
  - 대부분의 층은 가까운 128토큰 창 안만 보는 local attention이고, 3층마다 한 번씩 전체를 보는 global attention입니다. 위치 정보는 RoPE로 넣습니다.
  - 어휘 256,000개. 이 때문에 파라미터 1.406억 개 중 0.983억 개가 단어 임베딩입니다.
- **우리가 붙인 부분**: 마지막 hidden 384차원을 3개 라벨로 바꾸는 분류층(`classifier`, 384×3)입니다. `ModernBertForTokenClassification`을 씁니다.
- **인코더인 이유**: 인코더는 문장 전체를 양방향으로 한 번에 읽고, 모든 토큰에 대해 동시에 판단합니다. 그래서 한 번의 forward로 끝나 빠릅니다.

### 2.2 탐지 방식: BIO 토큰 분류

1. **토큰화와 창 나누기**: 텍스트를 토큰으로 나누고, 512토큰 창으로 자릅니다. 창은 128토큰씩 겹칩니다. 토크나이저가 토큰마다 원문 글자 위치(offset)를 함께 줍니다.
2. **토큰마다 분류**: 각 토큰이 `O`(비밀 아님), `B-SECRET`(비밀값 시작), `I-SECRET`(비밀값 계속) 중 무엇인지 확률을 냅니다(softmax).
3. **창 합치기**: 겹치는 부분의 토큰은 여러 창에서 나온 확률을 평균합니다. 창 경계에서 span이 잘리거나 두 번 나오는 것을 막습니다.
4. **span 만들기**: 확률이 가장 높은 라벨을 고르고, B로 시작해 I로 이어지는 토큰들을 한 span으로 묶습니다. 토큰의 글자 위치로 `[start, end)`를 정하고, 양끝의 공백만 뺍니다.
5. **점수와 cutoff**: span 점수는 그 토큰들의 "비밀일 확률"(P(B) + P(I))의 평균입니다. 점수가 cutoff 이상인 span만 남깁니다.

### 2.3 학습 방법

- **라벨 만들기**: 정답 글자 구간과 겹치는 토큰에 B 또는 I를, 나머지에 O를 붙입니다. 특수 토큰은 학습에서 뺍니다(`-100`).
- **손실 함수**: 토큰별 cross-entropy입니다. 라벨 가중치는 [O 1, B 2, I 2]입니다. 비밀 토큰이 아주 적어서, 가중치가 없으면 모델이 O라고 답하는 쪽으로 기울기 쉽기 때문입니다.
- **최적화**:
  - AdamW, 학습률 3e-5(고정), weight decay 0.01.
  - 배치 4. 길이가 비슷한 행끼리 묶어서 패딩을 줄입니다.
  - gradient clipping 1.0. 모델 전체(1.4억)를 학습합니다.
- **시작점**: mmBERT-small 원본에서 시작했습니다. 우리 v9·v10 모델에서 이어 학습하지 않았으므로, 결과는 팀 데이터만의 효과입니다.
- **epoch과 cutoff 선택**:
  - 최대 8 epoch을 돌립니다. epoch마다 val을 예측하고, cutoff 후보 7개(0.5~0.99) 중 F2가 가장 높은 것을 고릅니다.
  - val F2가 가장 좋은 epoch의 가중치만 저장합니다. 3 epoch 연속 좋아지지 않으면 멈춥니다(early stopping).
- **seed**: 110과 112 두 번 학습해서 seed에 따른 차이를 확인했습니다. 전달물은 seed 110입니다.
- **설정 파일**: `configs/span-pilot-step0-{a,b}.yaml`. A와 B는 데이터 폴더만 다르다는 것을 테스트로 확인합니다.

### 2.4 결과 (val, seed 110)

| 모델 | 선택 epoch | cutoff | 맞힘 / 오탐 / 놓침 | precision | F2 |
|---|---:|---:|---:|---:|---:|
| A (정답 435) | 2 | 0.99 | 388 / 47 / 47 | 0.892 | 0.892 |
| B (정답 615) | 3 | 0.90 | 551 / 55 / 64 | 0.909 | 0.899 |

### 2.5 약점: 경계 오류와 따옴표 정리

- **원인**: mmBERT 토크나이저는 `)";`나 `.",`처럼 이어진 구두점을 토큰 하나로 묶습니다.
  - 토큰 단위로 판단하는 모델은 비밀값과 닫는 따옴표 사이를 자를 수 없습니다.
  - A val 정답 435개 중 68개가 토큰 경계로는 정확히 표현할 수 없는 span입니다.
  - 그래서 오탐과 놓침이 짝으로 생깁니다. 위치는 거의 맞는데 따옴표 한 글자가 더 붙는 식입니다.
- **후처리(따옴표 정리)**: 예측 span의 경계를 규칙으로 고칩니다(`src/privai_model/ml_span/delimiters.py`).
  - **v1**: span 바로 앞에 여는 따옴표가 있고 span이 짝이 맞는 닫는 따옴표로 끝나면, 그 닫는 따옴표를 잘라 냅니다. 이스케이프된 `\"`나 값 자체가 따옴표로 끝나는 경우는 자르지 않습니다.
  - **v2**: v1 전에 시작 위치를 고칩니다. 값이 `+`, `#`, `%` 같은 구두점으로 시작해 span이 한 글자 늦거나 이르게 시작한 경우를 바로잡습니다.
  - 데이터의 정답 41,948개에 규칙을 적용해 봐도 바뀌는 정답은 0개였습니다. 맞힌 답을 틀리게 만들지 않습니다.

| 모델 | 정리 없음 | 정리 v1 | 정리 v2 |
|---|---:|---:|---:|
| A (435) | 388 / 47 / 47 · 0.892 | 428 / 7 / 7 · 0.984 | 435 / 0 / 0 · 1.000 |
| B (615) | 551 / 55 / 64 · 0.899 | 596 / 10 / 19 · 0.972 | 604 / 2 / 11 · 0.985 |

- v2는 A val의 오류를 보고 만들었습니다. 그래서 A val 1.000은 낙관적인 숫자입니다.
- 모델 폴더의 기본값은 정리 없음입니다. 켜려면 `span_bundle.json`에 `"delimiter_policy": "quote-delimiters-v2"`를 넣습니다.

## 3. Qwen 모델

### 3.1 모델 자체

- **기본 모델**: `Qwen/Qwen2.5-Coder-0.5B-Instruct`(revision `ea3f2471`). 코드로 많이 학습한, 지시를 따르도록 조정된 생성형 언어 모델입니다.
- **구조**:
  - Transformer 디코더 24층, hidden 896, FFN 4,864.
  - attention head 14개이고, key·value head는 2개만 둡니다(GQA). 메모리를 아끼는 방식입니다.
  - 어휘 151,936개, RoPE. 입력과 출력 임베딩을 공유하고, 파라미터는 약 4.94억 개입니다.
- **디코더인 이유**: 디코더는 앞에서부터 한 토큰씩 다음 토큰을 예측하며 글을 씁니다. 모델이 비밀값 문자열 자체를 출력하게 할 수 있습니다. 그러면 토큰 경계와 관계없이 글자 단위로 정확한 값을 낼 수 있습니다.

### 3.2 LoRA: 일부만 학습하기

- 기본 모델의 가중치 4.94억 개는 **고정**하고, 작은 어댑터만 학습합니다.
- 어댑터를 붙이는 곳은 각 층의 attention projection 4개(q, k, v, o)와 FFN projection 3개(gate, up, down)입니다.
- **원리**: 원래 가중치 행렬 W(d×k)는 그대로 두고, 작은 두 행렬 B(d×r)와 A(r×k)의 곱을 더합니다.
  - 식: W' = W + (α / r)·B·A
  - r = 16, α = 32이므로 더하는 양에 2배를 곱합니다. dropout은 0.05입니다.
- **학습 파라미터**: 층마다 366,592개, 24층 합계 **8,798,208개**입니다. 전체의 약 1.75%입니다.
- **장점**: 저장할 어댑터가 수십 MB로 작습니다. 기본 모델의 일반 능력을 덜 망가뜨리고, 적은 GPU 메모리로 학습할 수 있습니다.

### 3.3 탐지 방식: 값을 생성하고 위치는 직접 찾기

1. **프롬프트**: Qwen 채팅 형식으로 시스템 지시문과 텍스트를 줍니다.
   - 지시문에는 무엇이 비밀값이고 무엇이 아닌지(공개 식별자, 자리표시자, 가려진 값, 문서 예시, 해시 등)를 적었습니다.
   - 텍스트는 `<text>…</text>`로 감쌉니다. 정답을 암시할 수 있는 출처 정보는 넣지 않습니다.
2. **생성**: 모델이 `{"secrets":[{"value":"…","occurrence":n}]}` 형식으로 답합니다.
   - `value`는 원문에서 글자 그대로 복사한 비밀값입니다.
   - `occurrence`는 그 문자열이 원문에서 몇 번째로 나온 것인지(1부터)입니다.
   - 생성은 greedy decoding입니다. 매번 확률이 가장 높은 토큰을 고르고, 무작위 샘플링은 쓰지 않습니다. 같은 입력이면 같은 답이 나옵니다.
3. **위치 복원**: 모델은 글자 위치를 직접 내지 않습니다. 코드가 원문에서 `value`를 찾아, `occurrence`번째 등장 위치를 `[start, end)`로 정합니다.
   - 원문에 없는 값(hallucination)과 없는 등장 순번은 버립니다. 다른 위치로 "고쳐 주지" 않습니다.
   - JSON이 깨지면 span을 하나도 내지 않고 오류로 셉니다. 안전한 쪽으로 실패합니다.
4. **점수와 cutoff**: 값에 해당하는 생성 토큰들의 확률을 기하평균한 것이 점수입니다. 식은 exp(평균 log 확률)입니다. 점수가 cutoff 이상인 것만 남깁니다.

### 3.4 학습 방법

- **학습 데이터 형식(SFT)**: 각 행을 "프롬프트 → 정답 JSON" 대화 한 쌍으로 바꿉니다. 비밀값이 없는 행의 정답은 `{"secrets":[]}`입니다.
  - 바꾼 정답에서 위치를 다시 복원해 원래 정답과 같은지 확인했습니다. A 5,563/5,563, B 6,847/6,847이 모두 같았습니다.
- **손실 함수**: 정답 JSON 부분의 토큰에만 다음 토큰 cross-entropy를 겁니다(completion-only). 프롬프트와 원문은 맞히도록 학습하지 않고 읽기만 합니다.
  - 긴 입력에서 메모리를 아끼려고, 정답 위치의 hidden state에만 어휘 15만 개짜리 출력층을 계산합니다. 결과는 일반적인 방식과 수학적으로 같습니다.
- **최적화**:
  - AdamW, 학습률 2e-4, weight decay 0.
  - 처음 5% step 동안 학습률을 작은 값에서 2e-4까지 올리고(warmup), 그 뒤 cosine 곡선으로 0까지 줄입니다.
  - gradient clipping 1.0, 3 epoch.
- **배치**: 한 번에 1행씩 계산하고 gradient를 16행 모아서 한 번 업데이트합니다(gradient accumulation). 실제 배치 크기는 16입니다.
  - A는 epoch당 989 step, 모두 2,967 step입니다. B는 epoch당 1,212 step, 모두 3,636 step입니다.
- **메모리**:
  - 층의 중간 결과를 저장하지 않고 역전파 때 다시 계산합니다(gradient checkpointing).
  - 정밀도는 float32입니다. T4에서 B의 가장 긴 행(10,158토큰)이 최대 11.3GB(14.6GB 중)를 써서 들어갔습니다. bfloat16은 T4에서 오히려 메모리가 부족했습니다.
- **길이 제한**: 행을 자르지 않으려고 입력 최대 길이를 10,240토큰으로, 생성 최대 길이를 2,048토큰으로 늘렸습니다. 레시피에서 바꾼 것은 이 두 개뿐입니다.
- **환경**:
  - Colab T4에서 학습했습니다. 학습 시간만 A 약 6시간, B 약 8시간이고, step당 약 7.5초입니다.
  - 런타임이 4~7시간마다 끊겨서, Drive에 저장한 체크포인트(어댑터·optimizer·scheduler 상태와 데이터 위치)에서 이어서 학습했습니다.
- **epoch과 cutoff 선택**: epoch 1~3 어댑터로 val을 모두 예측합니다. 어댑터마다 관측된 모든 점수를 cutoff 후보로 놓고, F2가 가장 높은 조합을 고릅니다. 같으면 precision이 높은 쪽입니다.

### 3.5 결과 (val)

| 모델 | 선택 epoch | cutoff | 맞힘 / 오탐 / 놓침 | precision | F2 |
|---|---:|---:|---:|---:|---:|
| A (정답 435) | 3 | 0.958 | 430 / 1 / 5 | 0.998 | 0.990 |
| B (정답 615) | 3 | 0.983 | 591 / 2 / 24 | 0.997 | 0.968 |

- 후처리 없이 나온 숫자입니다. 값을 글자 그대로 출력하니 mmBERT의 따옴표 경계 오류가 거의 없습니다.
- 원문에 없는 값을 낸 경우는 A 5개, B 4개였습니다. B는 없는 등장 순번도 1개 냈습니다. 모두 span 없이 버려졌습니다.
- 정답이 없는 행에서 무언가를 찾은 경우는 둘 다 0행입니다.

## 4. 두 모델 비교

| | mmBERT | Qwen |
|---|---|---|
| 경계 정확도 | 토큰 경계에 묶임. 따옴표 정리 규칙이 필요 | 글자 단위로 정확. 후처리 없음 |
| 대표 오류 | 따옴표·구두점이 붙은 span | 원문에 없는 값 생성. 위치를 찾지 못하면 버림 |
| 속도 (예측) | 한 번의 forward로 끝남. 이 파일럿에서는 Qwen과 같은 조건으로 재지 않음 | 답을 한 토큰씩 생성. T4에서 입력 하나에 중앙값 0.2~1.2초, 느린 쪽 5%는 수 초~37초 |
| 학습 비용 | T4에서 1~2시간 | T4에서 6~8시간 |
| 모델 크기 | 가중치 563MB (float32) | 기본 모델 + 어댑터 수십 MB |
| 같은 val에서 F2 (후처리 없음) | A 0.892, B 0.899 | A 0.990, B 0.968 |
| 같은 val에서 F2 (mmBERT + 정리 v2) | A 1.000, B 0.985 (A는 낙관적) | – |

- **비교 조건**: 두 모델은 같은 val 파일(sha256 일치)과 같은 채점 함수(행 ID·시작·끝이 모두 같아야 맞힘)로 쟀습니다.
  - 다만 두 숫자 모두 epoch과 cutoff를 고른 그 val에서 잰 것이라 낙관적입니다. 독립된 비교는 팀 test로 해야 합니다.
  - cutoff 후보도 다릅니다. mmBERT는 고정된 7개(0.5~0.99)이고, Qwen은 관측된 점수 전부입니다. 다만 Qwen은 cutoff를 0으로 둬도 A 430/1/5(F2 0.990), B 591/4/24(F2 0.967)여서, 더 촘촘한 cutoff 덕은 거의 없습니다.
- 후처리 없이 비교하면 Qwen이 크게 앞섭니다.
- 따옴표 정리 v2를 켠 mmBERT는 B에서 Qwen보다 조금 높습니다(0.985 vs 0.968). 다만 그 규칙은 val 오류를 보고 만든 것이라 낙관적입니다.
- mmBERT는 빠르고, Qwen은 정확하지만 느립니다. 어느 쪽이 나은지는 팀의 test·test_ood 결과와 PromptGuard의 지연 요구로 판단해야 합니다.

### 4.1 팀 채점 규칙으로 다시 잰 val (비공식)

위 숫자는 우리 저장소의 채점 코드로 잰 것입니다. 팀 채점기(`promptguard-data` `metric-detection/scripts/evaluate.py`)와 규칙이 같은지 확인하려고, 같은 val 예측을 팀 규칙으로 다시 쟀습니다.

- **팀 채점기를 그대로 돌리지 않은 이유**: 팀 채점기는 train·val 세션을 일부러 거부합니다(`evaluation/run.py`의 `check_use`, 팀 commit `5d77a3e`). 그래서 채점 규칙만 가져왔습니다.
  - 가져온 것: `scorer/span_scoring.py`의 `score_item`과 `report/aggregate.py`의 F2 식(팀 commit `5b812c7`)
  - 예측 span 하나를 가림(edit) 하나로 넣었습니다. 겹치는 span은 합쳤습니다.
- **팀 규칙**:
  - recall은 정답 span이 정확히 가려진 비율입니다. 모두 덮고 밖으로 넘치지 않아야 합니다.
  - precision은 정답 span 안에 들어간 edit의 비율입니다.
- **빠진 것**: PromptGuard의 다른 탐지기와, 같은 값을 다시 가리는 처리는 들어가지 않았습니다. 팀이 PromptGuard를 거쳐 낼 숫자와 같지는 않습니다.
- **예측이 같은지 확인**:
  - mmBERT는 로컬(MPS)에서 다시 예측했고, 우리 채점 숫자가 이전과 정확히 같았습니다.
  - Qwen은 Drive의 epoch 3 예측에서 위치와 점수만 가져왔습니다. 행 순서와 내용은 해시로 확인했고, 선택 결과와 개수가 같았습니다.

| 모델 | 우리 채점 F2 | 팀 규칙 F2 | 팀 규칙 내역 (정확 / 넘침 / 일부만 / 놓침) | 팀 규칙 precision |
|---|---:|---:|---|---:|
| mmBERT A | 0.892 | 0.893 | 388 / 42 / 5 / 0 | 0.897 |
| mmBERT B | 0.899 | 0.900 | 551 / 50 / 4 / 10 | 0.914 |
| mmBERT A + 정리 v2 | 1.000 | 1.000 | 435 / 0 / 0 / 0 | 1.000 |
| mmBERT B + 정리 v2 | 0.985 | 0.985 | 604 / 0 / 1 / 10 | 0.998 |
| Qwen A | 0.990 | 0.990 | 430 / 0 / 0 / 5 | 0.998 |
| Qwen B | 0.968 | 0.968 | 591 / 0 / 1 / 23 | 0.998 |

- 두 채점 방식의 차이는 모든 경우 0.001 이하입니다. 비교 결론은 바뀌지 않습니다.
- 차이가 나는 곳은 정답보다 짧게 잡은 예측("일부만")입니다.
  - 우리 채점은 이를 오탐으로 셉니다.
  - 팀 규칙은 그 가림이 정답 안에 있으므로 precision에서 맞힘으로 셉니다. 그래서 팀 규칙의 precision이 조금 높습니다.
- 집계는 [`reports/ml_span/val-team-rules-pilot-step0.json`](../../reports/ml_span/val-team-rules-pilot-step0.json)에 있습니다. 다시 재려면 `scripts/score_val_team_rules.py`를 씁니다.

## 5. 아직 확인하지 않은 것
