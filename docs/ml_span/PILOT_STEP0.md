# 팀 0단계 파일럿: 모델 A와 B

팀의 ML 학습 데이터 0단계 묶음(`promptguard-data` 브랜치 `ml-train-pilot`, commit `5b812c7`)으로 모델 두 개를 학습했습니다. 목적은 LLM 템플릿을 더 만들 가치가 있는지 판단하는 것입니다. A와 B는 학습 설정이 같고, train·val 파일만 다릅니다.

- **A**: 손 템플릿 + privesc
- **B**: 손 템플릿 + LLM 템플릿 + privesc

**팀 test·test_ood는 열지 않았습니다.** 팀이 먼저 평가하기로 했으므로, 이 문서의 숫자는 모두 validation 또는 우리 개발셋 결과입니다. 집계는 `reports/ml_span/pilot-step0.json`에 있습니다. 개수·설정만 있고 값이나 원문은 없습니다.

## 학습 설정 (A와 B 동일)

`configs/span-pilot-step0-{a,b}.yaml`은 v10 base 레시피를 그대로 씁니다. 두 파일이 데이터 폴더 외에는 같다는 것을 테스트(`tests/ml_span/test_pilot_step0.py`)로 확인합니다.

- **시작 가중치**: mmBERT-small 원본(revision `abc3262`). 우리 v9·v10에서 이어 학습하지 않아, 결과는 팀 데이터만의 효과입니다.
- **하이퍼파라미터**: 학습률 3e-5, 배치 4(길이별로 묶음), 최대 8 epoch, patience 3, class weight [1, 2, 2], max_length 512, stride 128, seed 110.
- **선택 방식**: epoch와 cutoff는 각 모델 자신의 val에서 F2로 고릅니다. 팀 설계대로 A는 손 val, B는 손+LLM val입니다. 그래서 두 모델의 val 점수끼리는 비교하지 않습니다.
- **환경**: Colab Tesla T4, torch 2.14.1. A는 약 68분, B는 약 110분 걸렸습니다.

## 찾은 문제와 고친 것

### 1. B 학습이 손실 NaN으로 멈춤 → 학습 코드 수정

- **증상**: B 첫 학습은 epoch 1 도중 `nonfinite loss`로 멈췄습니다.
- **원인**: LLM 카드 `c0077`, `p0005`에 텍스트가 빈 item이 9개 있습니다. 길이별 묶기 때문에 이 빈 item들이 한 배치에 모였고, 정답 토큰이 하나도 없는 배치의 평균 손실은 0/0이 됩니다.
- **수정**: 학습 코드가 이런 배치를 건너뜁니다. A에는 빈 item이 없어 A 학습은 이 경로를 지나지 않습니다.
- **재학습**: B는 같은 seed로 다시 학습했고, 결과 이름은 `span-mmbert-pilot-step0-b-seed110`입니다.
- **팀에 알릴 것**: 빈 item 9개는 데이터 쪽 문제입니다.

### 2. 닫는 따옴표를 비밀값에 포함 → 따옴표 정리 옵션

- **증상**: A의 val 오류 47개는 모두 경계 오류였습니다. 놓친 비밀은 없었고, 엉뚱한 곳을 잡은 오탐도 없었습니다. 그중 41개가 값 끝의 닫는 따옴표까지 span에 넣은 경우입니다.
- **원인**: mmBERT 토크나이저는 `)";`, `.",`처럼 이어진 구두점을 토큰 하나로 묶습니다. 토큰 단위 모델은 값과 따옴표 사이를 자를 수 없습니다. val 정답 435개 중 68개가 토큰 경계로는 정확히 표현할 수 없는 span입니다(`alignment.json`).
- **정리 규칙**: 런타임 옵션 `delimiter_policy: quote-delimiters-v1`(`src/privai_model/ml_span/delimiters.py`)이 span 바로 앞의 여는 따옴표와 짝이 맞는 닫는 따옴표를 잘라냅니다. 그 뒤에 `;`, `,` 같은 구분자만 남을 때만 자릅니다.
  - 이스케이프된 `\"`는 자르지 않습니다.
  - 값 자체가 따옴표로 끝나는 경우(`""`)도 자르지 않습니다. 팀 데이터에 이런 정답이 135개 있었고, 이 정답들은 맞습니다.
- **안전성**: `data/`와 `runs/data`의 정답 41,948개 중 이 규칙으로 바뀌는 것은 0개입니다. 맞힌 답을 틀리게 만들 수 없습니다.
- **validation 결과**: 판정 기준은 F2 상승, precision 유지입니다. A와 B 모두 통과했습니다.
  - A: 40개 고침, 0개 망가짐
  - B: 45개 고침, 0개 망가짐
- **기존 모델**: 우리 경계 보정(boundary-v3)은 A에서 2개를 더 틀려 붙이지 않았습니다. v9와 v10에서는 이 규칙이 개발셋 오류를 몇 개 고쳤고(v4 9개, hold-out v11 3개 등) 망가뜨린 것은 없었습니다. 다만 두 모델 자신의 validation에는 해당 사례가 없어서 v9/v10 bundle에는 켜지 않았습니다. 아래 v2도 마찬가지입니다. v2는 v9·v10의 개발셋에서 v1보다 qwen_v2 1개, 팀 val 2개씩을 더 고쳤고, 자신의 validation은 바꾸지 않았습니다.

### 3. 값이 구두점으로 시작할 때 시작 위치가 한 칸 어긋남 → quote-delimiters-v2

- **증상**: 따옴표 정리(v1) 후 A에 남은 오류 7개는 모두 시작 위치 오류였습니다. B에서도 같은 유형이 9개 있었습니다.
  - 값이 `+`, `#`, `/`로 시작하면 토크나이저가 `"+`, `="#`처럼 앞의 따옴표와 첫 글자를 한 토큰으로 묶습니다. 그래서 span이 한 글자 늦게 시작합니다.
  - 값이 `%`, `_`로 시작하면 `:%`, `=_`처럼 앞의 구분자와 묶여, span이 구분자부터 시작합니다.
  - 시작이 어긋나면 v1이 여는 따옴표를 찾지 못해 닫는 따옴표도 남습니다.
- **규칙**(`quote-delimiters-v2`, 같은 모듈): v1을 적용하기 전에 시작 위치를 고칩니다.
  - span 바로 앞에 여는 따옴표와 구두점 1~3자가 있으면, 시작을 그 구두점으로 당깁니다. `>`, 괄호, 쉼표처럼 값 앞에 흔히 오는 문자는 제외합니다.
  - span이 키 이름 바로 뒤의 `=`나 `:`로 시작하면 그 구분자를 빼고, 그 뒤에 여는 따옴표가 있으면 따옴표도 뺍니다.
- **안전성**: 정답 41,948개 중 바뀌는 것은 0개입니다. 우리 개발셋과 상대 모델의 val에서도 망가뜨린 답이 없었습니다.

| 모델 (val 정답) | 정리 없음 | v1 | v2 |
|---|---:|---:|---:|
| A (435) | 388 / 47 / 47 · 0.892 | 428 / 7 / 7 · 0.984 | 435 / 0 / 0 · 1.000 |
| B (615) | 551 / 55 / 64 · 0.899 | 596 / 10 / 19 · 0.972 | 604 / 2 / 11 · 0.985 |

- **주의**: v2 규칙은 A의 validation 오류를 보고 만들었습니다. 그래서 A val 1.000은 낙관적인 숫자입니다. 독립적인 근거는 다른 셋입니다. v1 대비 B val에서 A가 8개를 더 고쳤고, qwen_v2에서 A가 1개를 더 고쳤습니다. 망가뜨린 것은 없었습니다. 실제 효과는 팀 test에서 확인해야 합니다.

- **양쪽 모두 상대 데이터에서 약합니다.** v10은 팀 val에서 F2 0.32~0.42이고, A·B는 우리 셋에서 오탐이 많습니다. 데이터마다 무엇을 비밀로 보는지(라벨 기준)와 문장 형식이 달라서, 한쪽 데이터만으로 학습한 모델은 다른 쪽 기준을 배우지 못합니다.
- **B가 A보다 넓게 일반화합니다.** 손 템플릿 val에서는 A와 같고(389 대 388), 우리 셋 7개 모두에서 오탐이 적습니다. F2는 v6을 빼고 모두 높습니다(v6은 B가 덜 잡고 더 놓침). LLM 템플릿이 손 템플릿 성능을 깎지 않으면서 다른 형식으로 넓혀 준다는 근거입니다. seed 112에서도 오탐이 적은 것은 같았고, F2는 v4·v6에서 A가 높았습니다(아래 "seed 변동"). 다만 결정은 팀 test로 해야 합니다.
- **팀 모델의 오탐 유형**(값은 보지 않고 문자 모양만 집계):
  - A는 negative_challenge에서 `artifact_sha256` 같은 해시 8개, `X-Request-ID` 값 6개, `[REDACTED]` 같은 가림 표시 8개를 비밀로 잡았습니다. B는 이 셋을 하나도 잡지 않았습니다.
  - B에 남은 오탐 16개 중 8개는 3자 소문자 단어라 PromptGuard의 6자 미만 필터에 걸립니다. 나머지 8개는 한국어 문장 속 무작위 문자열입니다.
  - fresh_test·hold-out의 오탐은 대부분 우리 hard negative입니다. 문맥상 비밀이 아니라고 밝힌 무작위 문자열(빌드 digest, 관측값, 예시 값)과 16자리 숫자입니다. 팀 데이터에는 이런 "비밀처럼 생겼지만 문맥상 아닌 값"이 적은 것으로 보입니다.
- **v10이 팀 val에서 놓치는 것**(B val 기준): PASSWORD 262개 중 159개를 놓칩니다. PRIVATE_KEY는 57개 중 정확히 맞힌 것이 없고 46개가 경계 불일치입니다. 팀 정답은 `-----BEGIN … KEY-----` 머리줄과 꼬리줄까지 포함하고, v10은 본문만 잡습니다(시작이 30~36자 늦고 끝이 약 30자 이릅니다). 라벨 기준 차이입니다.
- **팀에 제안할 데이터**: 해시·요청 ID·가림 표시·문맥상 예시 값 같은 hard negative를 train에 더하면 다른 출처에서의 오탐을 줄일 수 있을 것입니다. 단, 같은 템플릿과 형식의 positive와 짝을 지어 넣어야 합니다. 아래 B+HN 실험에서 negative만 더했더니 모델이 그 형식의 비밀을 아예 잡지 않게 됐습니다.

## 후속 실험: B에 우리 hard negative만 더하기 (B+HN)

팀 데이터로 학습한 모델이 우리 셋에서 오탐이 많아서, 우리 hard negative를 더하면 줄어드는지 확인했습니다.

- **데이터**: B train에 `data/span-context-v10/train.jsonl`의 비밀 없는 hard negative 3,208행을 더했습니다(`scripts/prepare_pilot_plus_ours.py bhn`). 더한 행은 우리 개발셋과 템플릿 family가 겹치지 않습니다. val, 설정, seed 110은 B와 같습니다.

칸은 맞힘 / 오탐 / 놓침 · F2입니다.

- **결과: 오탐은 거의 사라졌지만, 우리 형식의 비밀도 잡지 않게 됐습니다.** fresh_test와 v7에서 하나도 잡지 못했습니다. 더한 hard negative는 우리 생성기의 문장 형식인데, 같은 형식의 positive는 train에 없습니다. 그래서 모델은 문맥(예시 값, 해시, 가림 표시)이 아니라 "이 형식이면 비밀이 아니다"를 배웠습니다.
- 형식이 다른 qwen_v2(LLM이 쓴 문장)에서는 맞힘을 거의 유지하면서 오탐이 59에서 8로 줄었습니다. 문맥을 일부 배운 흔적일 수 있지만, 위의 지름길 때문에 따로 떼어 볼 수 없습니다.
- **B val만으로는 이 문제가 보이지 않습니다.** B val에는 우리 형식의 텍스트가 없기 때문입니다. 출처를 섞어 학습할 때는 validation에도 각 출처가 들어 있어야 합니다.
- **결론**: B+HN은 쓰지 않습니다. positive와 hard negative를 함께 더한 B+v10은 아래에 있습니다.

## 후속 실험: B에 우리 v10 train 전부 더하기 (B+v10)

- **데이터**: B train에 `data/span-context-v10/train.jsonl` 6,304행(positive 3,096, hard negative 3,208)을 더해 25,689행입니다(`scripts/prepare_pilot_plus_ours.py bv10`). validation은 B val(정답 615)과 v10 validation(정답 192)을 합친 셋에서 epoch과 cutoff를 고릅니다. 설정과 seed 110은 B와 같습니다.
- **학습 기록**:
  - 첫 학습은 Drive가 가득 차서 가중치가 저장되지 않았습니다. epoch 6까지 진행했고 가장 좋은 epoch은 3이었습니다.
  - 공간을 비우고 다시 학습했습니다. epoch 1~3의 결과가 첫 학습과 똑같아 재현성이 확인됐습니다.
  - 다시 학습한 run은 epoch 4 끝 무렵 Colab 런타임이 끊겼습니다. epoch 3 가중치는 저장되어 있었습니다. 첫 학습에서 epoch 4~6은 epoch 3보다 낮았으므로, 끝까지 학습했어도 epoch 3이 선택됐을 것입니다.

- **한 모델이 두 출처를 함께 배웠습니다.**
  - 팀 B val의 F2는 B와 거의 같습니다(0.896 대 0.899).
  - 우리 셋에서는 v10과 비슷합니다. v6과 qwen_v2는 v10보다 높고, v7은 낮습니다.
  - B+HN과 달리 우리 형식의 비밀도 잡습니다. hard negative는 같은 형식의 positive와 함께 넣어야 한다는 B+HN의 결론과 맞습니다.
- **대가: 팀 B val의 precision이 B보다 낮습니다.** precision은 0.890으로 B의 0.909·0.903보다 낮고, 오탐은 68개로 B의 55·59개보다 많습니다. 따옴표 정리 v2 후에도 오탐이 15개로 B의 2·6개보다 많습니다. 판정 기준으로 보면 F2는 seed 범위 안이지만 precision은 유지되지 않았습니다. v10 validation에서도 precision이 v10보다 조금 낮습니다(0.938 대 0.953).
- **B val에서 늘어난 오탐의 정체**(`scripts/colab_diag_pilot.sh`, 팀 val 라벨 기준, 개수만):

  - 경계 오류는 세 모델이 비슷하고, 따옴표 정리 v2가 거의 다 고칩니다.
  - B+v10이 더 낸 오탐은 모두 정답과 겹치지 않는 값입니다. 팀이 비밀이 아니라고 표시한 ID, base64, 개인정보, 리소스 이름(8개)과 표시 없는 문자열(5개)입니다. LLM 템플릿 쪽이 10개, 손 템플릿 쪽이 5개입니다(정리 후).
  - 우리 데이터의 비밀 기준이 팀보다 넓어서 생긴 차이로 보입니다. 우리 데이터는 ID처럼 생긴 무작위 문자열도 비밀로 표시하는 경우가 있고, 팀은 그런 값을 `identifier`로 따로 둡니다. 출처를 섞으려면 이런 값의 라벨 기준부터 맞춰야 합니다.
  - 놓친 비밀은 B+v10이 8개로 B(10개, 5개)와 비슷합니다.
- **주의**:
  - fresh_test는 v10 train과 같은 생성기에서 만든 test라 B+v10에 유리합니다.
  - 상대적으로 독립적인 근거는 hold-out v11과 qwen_v2입니다. hold-out v11에서는 v10과 F2가 같으면서 오탐이 83개에서 48개로 줄었습니다.
  - seed가 하나이고 끊긴 run입니다. 팀 test로 확인해야 합니다.
- **PRIVATE_KEY 라벨 기준은 충돌하지 않습니다.** v10 train에는 PEM 머리줄이 붙은 정답이 없습니다. 그래서 팀 기준(머리줄과 꼬리줄 포함)은 B train의 PEM 정답 473개만 가르칩니다.
- **팀에 제안**: 출처를 섞는다면 B+v10처럼 positive와 hard negative를 함께 넣고, validation에도 각 출처를 넣는 것이 좋습니다. 원하면 B+v10 체크포인트(Drive `span-mmbert-pilot-step0-bv10-seed110/`)도 팀 test로 평가할 수 있습니다.

## seed 변동

같은 레시피라도 seed에 따라 결과가 흔들릴 수 있습니다(v11 두 seed는 외부 F2가 0.367과 0.498). 그래서 A와 B를 seed 112로 한 번 더 학습했습니다(Colab T4, 설정은 seed만 다름). 맥 GPU에서 돌리던 A seed 111은 16GB 메모리의 스왑 때문에 배치당 17초까지 느려져 epoch 4 뒤에 멈췄습니다. 그때까지의 val F2는 0.894, 0.892, 0.894, 0.890으로 다른 seed와 같은 범위였지만, 끝나지 않은 run이라 표와 보고서에서는 뺐습니다.

- **따옴표 정리 v2**: seed 112에서도 망가뜨린 답 없이 A 45개, B 53개를 고쳤습니다. v2 규칙은 seed 110 A의 오류를 보고 만들었으므로 seed 112의 오류는 규칙을 만들 때 보지 않은 것입니다. 다만 같은 val 셋이라 완전히 독립적인 확인은 아닙니다.
- **다른 출처의 데이터에서는 seed 차이가 큽니다**(개발셋, 참고, 따옴표 정리 끈 숫자):
